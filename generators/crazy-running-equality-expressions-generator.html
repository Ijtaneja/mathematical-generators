Crazy Running Equality Expressions Generator

Created by Inder J. Taneja

Searches for identities where the digits 1–9 (ascending), 9–1 (descending), or 9–0 (descending through zero) each appear exactly once, in strict order, split across an equals sign into two sides that evaluate to the same value k.

digits: 123456789  |  987654321  |  9876543210
ops: + − × ÷   ^   √ (up to 4 nested roots)   !   (a!)! (factorial applied twice)   parentheses   unary −

The aim of the work is to bring expressions like these:

55 := 12/3+45+6 = 7+8*(sqrt(9))! 55 := (sqrt(9))!*8+7 = (65+43)/2+1
721 := 1+(2*3)! = -4+5+6! = -7+8+((sqrt(9))!)! 721 := ((sqrt(9))!)!+8-7 = 6!+5-4 = (3*2)!+1

Equality partitions split the digit run into contiguous, non-overlapping chunks (for example, a double equality may split 9 digits into three groups of 3) — every chunk still uses its digits exactly once, and no digit is ever shared between chunks. Double and triple equalities add search time because more partition points must be checked.

This only sets how many equations are shown per k when the search first finishes — every distinct equation the search actually finds for a k is stored and can be reached via the "showing" +/- control below, and downloads always include the full stored set, not just what's currently displayed. Results are ranked by a transparent complexity score, with the simplest verified identities first.

Interval mode retunes the search to favor values near your chosen range instead of small numbers — this is what makes ranges like 1010–1033 reachable, at the cost of no longer finding much outside it. Only the digit runs selected above are searched, and only k values inside [From, To] are kept.

Exact-target mode concentrates the search on one chosen value of k and retains only identities that pass a strict independent numerical recheck.

Click "Run search" to build the table. This runs entirely in your browser and typically takes 30–60 seconds — the progress line above shows which stage it's in.

Caps used for performance and safety: factorial argument limited to 0–12; factorial applied twice, written as (a!)!, limited to arguments 0–3 (since (4!)! would require 24!, which is astronomically large); exponent magnitude capped at ±10 unless the base is exactly −1, 0, or 1 (which allow arbitrarily large throwaway exponents, matching tricks like (9−8)^765); all intermediate values capped at 200,000 in magnitude (real targets stay far below that, and allowing bigger numbers mainly just multiplies the search space with useless giants); and at most 300 distinct values, 3 expression variants each, are kept per sub-expression, with smaller-magnitude integers kept in preference to larger ones when a sub-expression has to be trimmed. That last choice is a deliberate trade-off: it's what makes small-to-moderate k values (single and double digits, low hundreds) come back with dozens of representations, but it means very large targets — several thousand and up, the kind that need a surviving intermediate like 6! or 7! deep in the tree — are less likely to surface. If you want the search retuned to favor that high range instead, that's a small constant change away.
